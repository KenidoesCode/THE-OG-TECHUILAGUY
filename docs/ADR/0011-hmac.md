# ADR 0011: HMAC-SHA256

**Status:** Accepted. Continues Layer 10 (Cryptography) directly from
ADR 0006's SHA-256 — a real, small, standards-based MAC construction,
built by reusing the already-verified hash rather than adding a new
primitive family.

## Context

ADR 0006 named HMAC as the natural next step once SHA-256 existed
("several later pieces of this layer... will build directly on it").
A MAC (message authentication code) is also a genuine prerequisite for
authenticating RPC messages, storage records, or telemetry elsewhere
in this repository's later layers — none of that integration exists
yet, but the primitive needs to exist first.

## Decision

`10-cryptography/mac/hmac_sha256.cpp` implements HMAC exactly per
RFC 2104's construction (`H(key XOR opad || H(key XOR ipad || message))`),
instantiated with `H` = the existing `crypto::Sha256`/`crypto::sha256`
from `../hashing/sha256.hpp` — not a new hash, a real reuse within the
same layer. A key longer than SHA-256's 64-byte block size is hashed
down first per RFC 2104; a shorter key is zero-padded. Verified against
RFC 4231's own published test vectors, including specifically the
key-longer-than-block-size case (test case 6), which is the one branch
of the construction that's easy to get subtly wrong (e.g. forgetting
to zero-pad the *remainder* of the hashed-down key before XORing with
the pad constants).

`constantTimeEquals()` is included alongside the MAC itself because
comparing a computed MAC against an expected one with an ordinary
`==`/`memcmp` is a genuine, well-known vulnerability class (a timing
side channel revealing how many leading bytes matched, letting an
attacker forge a valid MAC byte-by-byte) — a MAC primitive without a
safe comparison function next to it is an incomplete, easy-to-misuse
building block.

## What this is not

- **Not a KDF.** HMAC is also the basis of HKDF (RFC 5869), which is
  not implemented — a MAC and a key-derivation function are different
  tools even though HKDF is built from HMAC.
- **Not integrated anywhere yet.** Nothing in RPC, storage, OGGit, or
  any other layer calls this yet — same as SHA-256's own status in ADR
  0006, this is a verified, standalone primitive ready to be built on.
- **Not hardened against all side channels.** `constantTimeEquals`
  addresses the specific, well-known MAC-comparison timing leak; the
  HMAC computation itself has not been audited for other side-channel
  concerns (e.g. cache-timing behavior of the underlying SHA-256
  implementation), consistent with SHA-256's own "not
  side-channel-hardened" caveat in ADR 0006.

## Tested invariants

`10-cryptography/tests/hmac_test.cpp` (6 hosted assertions): RFC 4231
test cases 1, 2, 3, and 6 (the last specifically exercising the
key-longer-than-block-size branch) all match exactly; two different
keys produce two different MACs for the identical message; and
`constantTimeEquals` correctly reports equal, unequal, and
length-mismatched buffer pairs.

## Consequences

Every claim about MACs/message authentication elsewhere in this
repository must describe this layer using the scope recorded here: a
verified HMAC-SHA256 implementation with a safe constant-time
comparison helper, not a KDF, not yet integrated anywhere. This ADR is
the single source of truth for that distinction until a future ADR
extends it.
